# Peers-SS — ТЗ сервиса для OpenWrt

Nov 20, 2026 · @Miffintos

## 1. Суть и принятые решения

Peers-SS — лёгкий сервис для OpenWrt 24.10.8 с podkop 0.7.24. Он держит назначенный конфиг StealthSurf (`vless://`) на роутерах клиента и при блокировке за 5 минут переводит все роутеры с этим конфигом на сервер в локации с минимальным пингом. Отдельно, на сервере администратора, работает Telegram-бот: он напоминает клиентам об окончании конфига и шлёт алерты администратору.

**Почему не нужен «главный» роутер.** Когда любой роутер меняет сервер через `PATCH /configs/:id/settings`, у конфига меняется `connection_url` прямо в StealthSurf, и старая ссылка перестаёт работать у всех. Остальным роутерам достаточно получить новую ссылку и вставить её в podkop.

**Термины**

- **Контур** — один клиент: его роутеры (в любых городах), его токен StealthSurf, его пароль шифрования. Контуры не видят друг друга.
- **Роутер (peer)** — роутер с Peers-SS. Все роутеры контура равны: одинаковый веб-интерфейс и общие настройки.
- **Группа peers-ss** — набор сред внутри контура. Имена по умолчанию: `peers-ss`, `peers-ss-2`, …
- **Среда** — роутеры + один конфиг. Это единица привязки: ротация касается всех роутеров всех сред с этим конфигом.
- **Ведомый роутер** — роутер без токена или с токеном другого аккаунта. Он применяет новые ссылки, но сам PATCH не делает.
- **Ротация** — перенос конфига на другой сервер после блокировки.

**Схемы привязки** — все три выражаются через среды, поэтому переход между ними сохраняет старые значения:

| Схема | Пример | Как устроена |
| --- | --- | --- |
| Одиночная | 1 роутер / 1 конфиг | Среда из 1 роутера |
| Групповая | peers-ss / 1 конфиг | Группа с одной средой на все роутеры |
| Сложная | 2+1 / 2 конфига, 3×1 / 3, 3×2 / 3 | Группа с несколькими средами, у каждой свой конфиг |

**Принятые решения**

| Вопрос | Решение |
| --- | --- |
| Формат конфига | Всегда `vless://`; вставка в podkop 0.7.24 и применение |
| Новая локация при блокировке | Любая, кроме «Умной» и «России», с минимальным пингом от роутера, где случилась блокировка |
| Кто ротирует | Роутер, увидевший блокировку; если у него нет подходящего токена — другой роутер этой привязки с токеном |
| Общее хранилище | Приватный репозиторий GitHub, папка на контур, данные зашифрованы паролем контура |
| Токен StealthSurf | Один на роутере, вводится вручную (виден при вводе); можно добавить позже, заменить, удалить |
| Один конфиг в нескольких средах | Разрешено; такие среды ротируются вместе |
| Техработы, массовая блокировка | Повтор каждые 10 минут с одного роутера, пока не заработает |
| Уведомления | Telegram-бот на Ubuntu-сервере администратора: клиенту — за 3 дня и каждый день до окончания, в 21:00 МСК; администратору — алерты |
| Доступ к LuCI | Только администратор (root); клиенты свой конфиг видят через бота |
| Тестирование | Отдельный конфиг StealthSurf `Test-conf` |
| Минимальный роутер клиента | 128 МБ флеша, 256 МБ ОЗУ |

## 2. Архитектура

На каждом роутере контура стоят одни и те же части; общих точек три: хранилище GitHub, API StealthSurf и бот на сервере администратора.

&#91;embedded content: архитектура Peers-SS · роутер, хранилище, API, бот\]

Роутер, заметивший блокировку, переносит конфиг через API и кладёт новую ссылку в `rotations/`; остальные роутеры с этим конфигом забирают её в течение минуты и вставляют в свой podkop. Бот ничего не пишет на роутеры: он читает карточки и алерты из хранилища и шлёт сообщения в Telegram.

## 3. Модель данных

Хранилище — приватный репозиторий `peers-ss-state` (отдельный от кода), одна папка на контур. Содержимое файлов зашифровано паролем контура; в открытом виде только имена файлов и номер схемы данных. Каждый роутер пишет в основном свой файл, поэтому конфликтов записи почти нет.

| Файл | Кто пишет | Когда | Что хранит |
| --- | --- | --- | --- |
| `<контур>/contour.json` | любой роутер из LuCI | при правках | группы, среды, имена роутеров, привязки конфигов, общие настройки, архив привязок |
| `<контур>/routers/<router_id>.json` | сам роутер; другие — при переименовании | при смене состояния и раз в 6 ч | статус, пинг через `vless`, последний контакт, хэш применённой ссылки, есть ли токен и какого аккаунта |
| `<контур>/rotations/<account>-<config>.json` | роутер, делающий ротацию | при ротации | замок, ревизия, новая `vless://`, последние 10 ротаций, чёрный список серверов на 24 ч |
| `<контур>/invites/<invite_id>.json` | любой роутер | создание и использование ссылки | целевая группа и среда, срок, хэш кода, кем использована |
| `<контур>/cards/<account>-<config>.json` | один роутер с токеном | раз в 6 ч | карточка для бота: название конфига, `expires_at`, автопродление, существует ли конфиг. Без ссылок и токенов, зашифрована ключом бота |
| <контур>/alerts/<событие>.json | роутер, заметивший событие | при событии, не чаще раза в 6 ч на одно событие | алерт для администратора (раздел 9), зашифрован ключом бота |

Пример `contour.json` (как он выглядит после расшифровки):

```json
{
  "schema": 1,
  "rev": 27,
  "name": "Иванов",
  "settings": {"check_interval_s": 45, "fail_threshold": 3, "retry_min": 10,
               "exclude_locations": ["smart", "RU"], "podkop_section": "peers_ss"},
  "groups": {
    "g1": {"name": "peers-ss", "envs": {
      "e1": {"name": "среда-1", "config": "8812:456", "routers": ["r1", "r2"]},
      "e2": {"name": "среда-2", "config": "8812:789", "routers": ["r3"]}
    }}
  },
  "standalone": {"e3": {"config": "8812:456", "routers": ["r4"]}},
  "routers": {"r1": {"name": "openwrt-1"}, "r2": {"name": "openwrt-2"},
              "r3": {"name": "openwrt-3"}, "r4": {"name": "openwrt-4"}},
  "archive": [{"at": 1795688820, "group": "g1", "env": "e2", "config": "8812:789"}],
  "next_router_num": 5
}
```

**Правила**

- Привязка конфига = `<ID аккаунта>:<config_id>`. ID аккаунта берётся из `GET /profile` при вводе токена, поэтому замена токена того же аккаунта не ломает привязки.
- Роутер всегда ровно в одной среде. Его конфиг = конфиг этой среды.
- Ротируются вместе все роутеры всех сред контура с одинаковой привязкой.
- Смена схемы = слияние или разделение сред. Привязки, которые перестали использоваться, уходят в `archive` с датой; при обратном разделении LuCI предлагает их восстановить.
- Запись — через GitHub Contents API с `sha` текущей версии. Это атомарная проверка: из двух одновременных записей проходит только одна. Проигравший перечитывает файл и повторяет; если правка шла из LuCI — показывает «изменено на openwrt-N, обновите страницу».
- Опрос — с `If-None-Match`; ответ 304 не тратит лимит GitHub.
- Сроки замков считаются по заголовку `Date` ответа GitHub, а не по часам роутера.
- Шифрование — AES-256 через пакет `uencrypt` (≈10 КБ). Ключ выводится из пароля контура и соли контура многократным SHA-256. Агент проверяет наличие пакета для 24.10 и выбирает вариант на mbedtls или wolfssl по прошивке.
- Поле `schema`: роутер со старой версией сервиса видит схему новее своей → ничего не пишет и показывает «обновите Peers-SS».

**Локально на роутере**

- `/etc/config/peers-ss` (UCI): `router_id`, `contour_id`, репозиторий, секция podkop.
- `/etc/peers-ss/secrets` (права 600, зашифрован): токен StealthSurf, токен GitHub, ключ контура. Честно: это защита от случайного просмотра и утечки бэкапа, но не от того, у кого есть root.
- `/tmp/peers-ss/` (ОЗУ): расшифрованный кэш, ETag, счётчики проверок. Флеш не изнашивается.
- Файлы сервиса добавляются в `/etc/sysupgrade.conf`, чтобы настройки пережили прошивку.

## 4. Установка, регистрация и токен

Установщик один (`install.sh` в репозитории кода), режимов два: новый контур на первом роутере и следующий роутер по одноразовой ссылке. Команда через pipe, потому что `ash` в OpenWrt не понимает `<(…)`. Всё, что вводится (пароль, токены), показывается на экране, чтобы было видно, правильно ли введено.

**Режим А — первый роутер нового контура**

```sh
wget -qO- https://raw.githubusercontent.com/<you>/peers-ss/main/install.sh | sh
```

1. Проверить: OpenWrt 24.10.x; podkop 0.7.24 установлен и запущен; есть `ucode`, `rpcd-mod-ucode`, `curl`, `uencrypt`; свободное место. Недостающие мелкие пакеты (`curl`, `uencrypt`) предложить поставить через `opkg`. podkop сам не ставить — сказать, чего нет, и остановиться.
2. Спросить имя контура (например, фамилию клиента) и пароль контура — дважды.
3. Спросить репозиторий хранилища (`owner/peers-ss-state`) и fine-grained токен GitHub с правом Contents: Read and write только на этот репозиторий.
4. Спросить токен StealthSurf (`stlth_…`). Можно пропустить — «добавить позже». Если введён: `GET /profile` → показать аккаунт; `GET /configs` → оставить только `vless` и вывести нумерованный список; выбор по номеру. Нет ни одного `vless`-конфига → предупреждение «аккаунт пуст».
5. Автоматически создать контур, группу `peers-ss`, среду `среда-1` с выбранным конфигом и зарегистрировать роутер как `openwrt-1`.
6. Выбрать секцию podkop: показать по номерам секции с `connection_type 'proxy'`; если таких нет — создать секцию `peers_ss` и сказать, что списки доменов для неё задаются в LuCI podkop.
7. Вставить `vless://`, применить, пройти диагностику (раздел 7), поставить LuCI, запустить службу.

Без токена роутер работает как ведомый: конфиг можно назначить позже из LuCI с любого роутера контура.

**Режим Б — следующий роутер по ссылке**

В LuCI на любом роутере контура: «Добавить роутер» → выбрать группу и среду (или «новая среда», или «одиночный») → срок действия (по умолчанию 24 ч) → «Создать ссылку». LuCI показывает готовую команду с кнопкой «Копировать»:

```sh
wget -qO- https://raw.githubusercontent.com/<you>/peers-ss/main/install.sh | sh -s -- --join PSS1.eyJjIjoiaXZhbm92IiwiLi4uIjoiLi4uIn0
```

1. Код `PSS1.…` = base64url от JSON: репозиторий, токен GitHub, `contour_id`, `invite_id`, секрет ссылки. Токена StealthSurf и пароля контура в нём нет.
2. Установщик спрашивает пароль контура и расшифровывает `contour.json`. Неверный пароль → повторить ввод.
3. Проверяет `invites/<invite_id>.json`: ссылка существует, не истекла, не использована, хэш секрета совпадает. Иначе — отказ с понятной причиной.
4. Регистрирует роутер в выбранной среде как `openwrt-N` и помечает ссылку использованной.
5. Спрашивает токен StealthSurf (можно пропустить). Если аккаунт токена не совпадает с аккаунтом конфига среды → предупреждение «роутер будет ведомым».
6. Берёт текущую `vless://` среды из хранилища (файл `rotations/` всегда хранит актуальную ссылку, не только после ротации), вставляет в podkop, применяет, запускает диагностику, ставит LuCI и службу.

**Управление токеном** (вкладка «Токен» в LuCI и `peers-ss token set|show|check|delete`)

- Токен один на роутере. У него есть метка, например «Аккаунт Иванова».
- Проверка показывает аккаунт, число `vless`-конфигов и ближайшую дату окончания.
- Замена токеном того же аккаунта — привязки работают дальше. Токен другого аккаунта — LuCI заранее показывает, по каким привязкам роутер станет ведомым.
- Удаление — роутер становится ведомым по всем привязкам.

**Безопасность ссылки**

- Одноразовая, срок по умолчанию 24 ч, отзывается в LuCI.
- Без пароля контура данные контура по ней не прочитать. Но в ней есть токен GitHub с правом записи, поэтому передавать её как пароль. Полный отзыв — заменить токен GitHub на всех роутерах контура (`peers-ss github-token set`).

**Удаление**: `peers-ss uninstall` убирает файлы и службу, снимает роутер из `contour.json`. Секцию podkop и текущую ссылку в ней не трогает.

## 5. Блокировка и ротация за 5 минут

Бюджет до применения новой ссылки на всех роутерах: обнаружение до 2 мин 15 с (3 проверки по 45 с) + ротация до 60 с + доставка остальным до 60 с + применение около 10 с ≈ 4,5 мин. Новая ссылка расходится через хранилище, а не через `GET /configs`, у которого кэш 300 с.

**Проверка (каждые 45 с на каждом роутере)** — 4 слоя, чтобы не путать блокировку с другими сбоями:

| Слой | Как проверяем | Не прошла → |
| --- | --- | --- |
| 1. Прямой интернет | HTTPS к 2–3 известным хостам мимо туннеля | Нет интернета у провайдера: ротации нет, счётчик не растёт |
| 2. podkop жив | служба podkop и процесс sing-box | Перезапустить podkop, счётчик не растёт |
| 3. Сервер доступен напрямую | TCP к `host:port` из `vless://`, мимо туннеля | Счётчик +1 (блок по IP или сервер лёг) |
| 4. Туннель пропускает трафик | запрос к `https://www.gstatic.com/generate_204` через `mixed_proxy` секции podkop | Счётчик +1 (блок протокола) |

Три сбоя подряд → конфиг считается заблокированным на этом роутере.

**Защита от плохого канала.** Если один роутер дважды за 30 мин вызвал ротацию, а остальные роутеры привязки в это время проходили проверку, его сигналы игнорируются 1 час. В LuCI он помечен «плохой канал», администратору уходит алерт.

**Кто ротирует.** Роутер, увидевший блокировку, если у него токен того же аккаунта, что и конфиг. Ведомый роутер записывает в `rotations/…` отчёт «заблокировано у меня» вместе со своими замерами пинга, и ротацию берёт первый роутер этой привязки с токеном. Нет ни одного роутера с токеном → алерт «некому ротировать».

**Ротация**

1. Прочитать `rotations/<account>-<config>.json`. Ревизия новее применённой → просто применить ссылку оттуда, конец.
2. Взять замок: записать `lock = {by: я, until: время GitHub + 180 с}` с проверкой `sha`. Не получилось или замок чужой и живой → ждать новую ссылку до 3 мин.
3. Ещё раз прогнать слои 3–4. Заработало → снять замок, конец.
4. `GET /configs` → текущие `server_id`, `location_id`, `connection_url` и флаги (из JSON `xray_config`). Если `connection_url` уже не та, что у меня (сменили в консоли или другой контур с тем же аккаунтом) → записать её в файл, применить, снять замок.
5. `GET /locations` → активные локации, кроме «Умной» и «России» (как они помечены — `tags`, `code` или `title` — агент проверяет на реальном ответе). Пропинговать все `ping_ip` параллельно напрямую: `ping -c 2 -W 1`, при закрытом ICMP — время TCP-соединения. Отсортировать по возрастанию.
6. Для лучшей локации `GET /configs/available-servers?location_id=…&protocol=vless` → до 5 серверов. Убрать текущий и серверы из чёрного списка, пропинговать, отсортировать.
7. `PATCH /configs/<id>/settings`: `location_id`, `protocol: "vless"`, `server_ids` по возрастанию пинга, все прежние флаги. Ошибки 9, 52, 53 (нет серверов, недоступен, полон) → следующая локация; 429 → ждать `Retry-After`.
8. Записать в файл: ревизия +1, новая `vless://`, запись в истории, старый сервер в чёрный список на 24 ч, `lock = null`.
9. Применить у себя и пройти диагностику (раздел 7). Не прошла → следующий кандидат, максимум 3 подряд.

**Остальные роутеры привязки**

- Раз в 45–60 с читают `rotations/…` с `If-None-Match` (304 бесплатно).
- Ревизия новее применённой → вставить ссылку в podkop, применить, диагностика, обновить свой статус.
- Страховка: один роутер с токеном раз в 10 мин сверяет `connection_url` из API с файлом. Расхождение (ручная смена в консоли) → записать новую ссылку в файл.

**Техработы и массовая блокировка**

- 3 кандидата подряд не прошли диагностику → состояние «Ожидание: техработы или массовая блокировка», алерт администратору.
- Дальше каждые 10 мин один роутер (через тот же замок) пробует следующего кандидата. Остальные ждут ссылку.
- В обычном режиме — не больше одной ротации привязки за 10 мин.
- Замок пропавшего роутера истекает сам через 180 с.
- Ручной запуск: кнопка «Сменить сервер сейчас» в LuCI и `peers-ss rotate`.

**Если GitHub недоступен**

- Взять замок нельзя. Если GitHub не отвечает 3 минуты, роутер с токеном ротирует без замка: случайная пауза 0–90 с, затем `GET /configs`. Если `connection_url` уже не та, что у роутера, — применить её; иначе `PATCH`.
- Пока GitHub недоступен, роутеры с токеном сверяют ссылку с API каждые 2 минуты, а не каждые 10, и так получают новую ссылку без хранилища.
- Ведомые роутеры без токена ждут возвращения GitHub: другого источника ссылки у них нет.
- Когда GitHub вернётся, ротатор дописывает в `rotations/…` ревизию с новой ссылкой, чтобы остальные выровнялись.
- Остаточный риск: из-за кэша `GET /configs` (до 300 с) в этом режиме два роутера могут сменить сервер дважды. Случайная пауза снижает риск, но не исключает его; в отчёт этапа 5 добавить проверку «GitHub недоступен».

## 6. API StealthSurf

Сервису хватает пяти методов. Адрес `https://api.stealthsurf.net` (без префикса `/v1`), заголовок `Authorization: Bearer stlth_…`, ответ всегда в обёртке `{status, statusCode, data}` ([общая информация](https://docs.stealthsurf.net/api)).

| Метод | Зачем | Лимит |
| --- | --- | --- |
| `GET /profile` | проверить токен, узнать ID аккаунта для привязок | 60 за 60 с |
| `GET /configs` | список конфигов: `connection_url`, `server_id`, `location_id`, `expires_at`, `auto_renewal`, `is_online`, флаги в `xray_config`; кэш 300 с | 60 за 60 с |
| `GET /locations` | все локации: `id`, `code`, `title`, `tags`, `is_active`, `ping_ip` для замера пинга | 60 за 60 с |
| `GET /configs/available-servers` | до 5 свободных серверов локации (по возможности из разных /24); кэш 10 с | 5 за 5 с |
| `PATCH /configs/:id/settings` | перенести конфиг на другой сервер или в другую локацию | 1 за 1 с |

Полные описания: [каталог методов](https://docs.stealthsurf.net/api/endpoints), [конфигурации](https://docs.stealthsurf.net/api/methods/configs), [локации](https://docs.stealthsurf.net/api/methods/locations), [модели данных](https://docs.stealthsurf.net/api/models).

**Подводные камни**

- Лимиты считаются на пользователя и метод, а не на токен: все роутеры одного аккаунта делят одно окно. Поэтому `GET /configs` делает только один роутер привязки раз в 10 мин (сверка) и раз в 6 ч (карточки для бота), плюс ротатор.
- `PATCH …/settings` пересоздаёт конфиг: неуказанные флаги могут сброситься. Перед `PATCH` прочитать флаги из JSON `xray_config` (`is_warp_enabled`, `is_reality_disabled`, `is_sni_changed`, `is_xhttp_enabled` и т.д.) и передать их снова под именами тела запроса (`use_warp`, `disable_reality`, `change_sni`, `use_xhttp` …). Соответствие полей агент сверяет с [моделями данных](https://docs.stealthsurf.net/api/models).
- В `PATCH` обязательны `location_id` и `protocol`; `server_id` и непустой `server_ids` вместе нельзя. `server_ids` — до 50 ID в порядке возрастания задержки, сервис берёт первый подходящий.
- Флаг `cantChangeSettings` запрещает смену (`BAD_REQUEST`) → алерт «конфиг нельзя перенастроить».
- Ошибки: бизнес-ошибка = HTTP 400 с `errorCode`; неверный токен = 401 → алерт «токен недействителен»; лимит = 429 с `Retry-After`; лимитер недоступен = 503.
- Во время ротации туннель не работает, поэтому `api.stealthsurf.net` и `api.github.com` должны открываться напрямую. В podkop у вас `enable_output_network_interface '0'`: запросы самого роутера идут мимо туннеля. Установщик проверяет эту опцию; если она включена — добавляет оба домена в исключения podkop.
- Перед `PATCH` в консоли просят отметку «конфиг сейчас не используется» ([инструкция](https://docs.stealthsurf.net/console/change-location)). Для ротации это нормально: старый сервер всё равно заблокирован.

## 7. podkop 0.7.24: вставка, применение, диагностика

Итог работы сервиса на каждом роутере — новая `vless://` в podkop, применённые изменения, пройденная диагностика и замеренный пинг через `vless`. Peers-SS меняет в podkop ровно одно поле — строку прокси управляемой секции. Списки доменов, другие секции и DNS не трогаются.

**Цикл применения**

1. Проверить ссылку: начинается с `vless://`, не пустая, отличается от текущей. Одинаковая → ничего не делать, флеш не пишется.
2. Перед самым первым изменением сохранить копию `/etc/config/podkop` в `/etc/peers-ss/podkop.orig`. Перед каждым — текущую ссылку в `/tmp/peers-ss/podkop.prev`.
3. Записать и применить через UCI (ориентировочно, точные имена — из podkop 0.7.24):

   ```sh
   uci set podkop.peers_ss.proxy_config_type='url'
   uci set podkop.peers_ss.proxy_string='vless://…'
   uci commit podkop
   /etc/init.d/podkop reload   # или restart — как делает «Применить» в LuCI podkop
   ```
4. Подождать 30–60 с: каждые 5 с проверять, что sing-box поднялся и проходит слой 4 из раздела 5; не дольше 60 с.
5. Запустить диагностику podkop — те же проверки, что на вкладке диагностики LuCI podkop. Команды агент берёт из `/usr/bin/podkop` версии 0.7.24.
6. Снять пинг через `vless`: тест задержки sing-box (Clash API), если podkop его открывает; иначе 3 запроса к `generate_204` через `mixed_proxy` секции (`curl -x socks5h://127.0.0.1:<порт> -w %{time_total}`), взять медиану.
7. Записать результат в `routers/<id>.json`: статус, пинг в мс, время, краткий итог диагностики. Он виден на вкладке «Обзор». Провал на роутере-ротаторе → следующий кандидат (раздел 5).

**Важно для агента**

- На тестовом роутере podkop и sing-box сейчас не видны в `opkg list-installed`, хотя `/etc/config/podkop` есть. Сначала установить podkop 0.7.24 и убедиться, что он работает.
- Не угадывать имена секций и опций: прочитать `/etc/config/podkop`, init-скрипт и LuCI-страницу podkop 0.7.24 и повторить ровно то, что делает его кнопка «Применить».
- Для проверки туннеля включить у управляемой секции `mixed_proxy_enabled`. Если podkop слушает этот порт на LAN-адресе, а не на `127.0.0.1`, — записать это в отчёт разведки.
- Хвост ссылки `#имя` можно заменить на название конфига, только если podkop это не ломает.
- После обновления podkop при старте службы проверять, что управляемая секция и опция на месте. Иначе статус «podkop изменился, нужна перенастройка» и алерт администратору.
- В секции `KCA` тестового роутера в `remote_domain_lists` стоит ссылка входа Tailscale, а не список доменов. Её нужно убрать до тестов, иначе диагностика podkop будет давать ложные ошибки.

## 8. Веб-интерфейс LuCI

Пункт меню **Services → Peers-SS** (`admin/services/peers-ss`), несколько вкладок, как у podkop. На всех роутерах контура интерфейс и настройки одинаковые; локальны только токен StealthSurf, пароль контура и ID роутера. Доступ — только у администратора (root).

| Вкладка | Что видно | Действия |
| --- | --- | --- |
| Обзор | этот роутер: имя, группа и среда, назначенный конфиг (название, локация, срок), пинг через `vless`, итог диагностики, последняя ротация, алерты | «Проверить сейчас», «Сменить сервер сейчас» |
| Группы и среды | группы peers-ss, среды внутри, конфиг каждой среды, число роутеров, статус | «Состав», «Создать группу / среду», «Переименовать», «Назначить конфиг», «Сменить схему», «Удалить» (только пустую) |
| Устройства | все роутеры контура: имя, группа, среда, токен есть/нет (ведомый), последний контакт, пинг, статус | «Переименовать», «Перенести в группу или среду», «Сделать одиночным», «Убрать из контура» |
| Добавить роутер | активные ссылки: группа, среда, срок, использована ли | «Создать ссылку», «Копировать команду», «Отозвать» |
| Токен | токен этого роутера с меткой, аккаунт, число `vless`-конфигов, ближайшее окончание | «Показать / скрыть», «Проверить», «Заменить», «Удалить» |
| Уведомления | ключ бота (один на все контуры), какие карточки и алерты уходят боту | «Отправить тестовый алерт» (бот перешлёт его администратору) |
| Настройки | интервал и порог проверок, интервал повтора (10 мин), исключённые локации, секция podkop, репозиторий хранилища | «Сменить пароль контура», «Проверить связь с API и GitHub» |
| Диагностика | журнал событий, диагностика podkop, история ротаций | «Пробная ротация» (всё, кроме `PATCH`), «Скачать отчёт» без секретов |

**Кнопка «Состав»** у группы или среды открывает окно: сколько в ней роутеров, их имена со статусом и последним контактом, какой конфиг привязан (название, локация, срок, текущий сервер).

**Выбор конфига.** На «Обзоре» виден только назначенный конфиг. Полный список `vless`-конфигов токена появляется лишь в окне «Назначить конфиг». Если у роутера, с которого делают правку, нет токена нужного аккаунта, окно предлагает выбрать роутер контура, через чей токен получить список.

**Смена схемы** (одиночная ↔ групповая ↔ сложная) — мастер в 2–3 шага: что объединить или разделить, какой конфиг остаётся у каждой среды. Убранные привязки уходят в архив; при обратном переходе мастер предлагает их восстановить.

**Правила интерфейса**

- Любая правка пишется в общий `contour.json`; остальные роутеры видят её в течение минуты.
- Одновременная правка с двух роутеров: сохранение проходит, только если с момента открытия страницы ничего не менялось. Иначе — «Настройки изменены на openwrt-N, обновите страницу», правка не теряется молча.
- Имена по умолчанию: роутеры `openwrt-1`, `openwrt-2`, …; группы `peers-ss`, `peers-ss-2`, …; среды `среда-1`, …. Имена 1–32 символа, уникальны внутри контура. Системный hostname роутера не меняется.
- Токены на странице по умолчанию скрыты, показываются кнопкой.
- Долгие операции (ротация, диагностика) выполняет служба; страница опрашивает статус и показывает прогресс.

**Техника**: клиентские JS-представления LuCI (`view`, `form`, `ui`, `rpc`), бэкенд — rpcd-плагин на ucode `/usr/share/rpcd/ucode/peers-ss.uc` с методами вроде `status`, `contour_get`, `contour_save`, `invite_create`, `invite_revoke`, `token_set`, `token_check`, `rotate_now`, `diag_run`. Права — ACL `luci-app-peers-ss.json`, меню — `menu.d/luci-app-peers-ss.json`.

## 9. Telegram-бот

Бот работает на Ubuntu-сервере администратора в КР, где Telegram доступен без проблем. Роутеры с Telegram не общаются вообще: они кладут в хранилище карточки конфигов и алерты, зашифрованные ключом бота, а бот раз в 5 минут их читает (с `If-None-Match`). Так токен бота не лежит на роутерах, а уведомления не дублируются.

**Регистрация клиента**

1. Клиент открывает бота, жмёт Start и отправляет свой ник (любой текст).
2. Администратору приходит: «Новый клиент: Иван (@ivan) — привязать?» и кнопки выбора контура, затем конфига (из карточек).
3. Администратор выбирает конфиг, клиенту приходит «Подключено: Дом Москва, действует до 20.12.2026».

Привязка идёт к `chat_id`, а не к нику: ник можно сменить или подделать, `chat_id` постоянный. Ник нужен администратору, чтобы узнать человека. Одному клиенту можно привязать несколько конфигов, одному конфигу — несколько клиентов.

**Напоминания клиенту** — только про конфиг, независимо от того, чей токен:

- За 3 дня до `expires_at` и далее каждый день в 21:00 по Москве: «Конфиг „Дом Москва“ заканчивается 20.12.2026 (через 2 дня)».
- В день окончания — «заканчивается сегодня»; на следующий день — одно сообщение «истёк», дальше тишина.
- После продления дата в карточке сдвигается, и напоминания прекращаются сами.
- Карточка старше 24 ч → клиенту ничего не шлём, администратору алерт «нет свежих данных по конфигу».

**Алерты администратору** — сразу, не дожидаясь 21:00, одно событие не чаще раза в 6 ч:

| Событие | Откуда |
| --- | --- |
| Блокировка и успешная ротация (для сведения) | роутер-ротатор |
| Ротация не помогает, режим ожидания | роутер-ротатор |
| Роутер не на связи больше часа | бот по `routers/` не видит, поэтому сигнал пишет любой роутер контура |
| Аккаунт пуст / конфиг исчез / токен недействителен / `cantChangeSettings` | роутер с токеном |
| Нет ни одного роутера с токеном для привязки | любой роутер контура |
| Плохой канал, podkop изменился | сам роутер |

**Админка** (только `chat_id` администратора): список клиентов и их конфигов, привязать / отвязать, все конфиги всех контуров со сроками, роутеры контура со статусами, новые заявки, «тихий режим» для алертов на N часов.

**Техника**: Python 3 на Ubuntu 24, long polling (входящие порты не нужны), SQLite для клиентов, привязок и отправленных уведомлений, служба systemd, расписание в часовом поясе `Europe/Moscow`. Если сервер был выключен в 21:00 — сегодняшние напоминания уходят сразу после запуска, один раз. Токен бота, ключ бота и токен GitHub только на чтение — в `/etc/peers-ss-bot/env` (права 600). Раз в сутки зашифрованная копия базы бота кладётся в хранилище. Код бота — в папке `bot/` репозитория кода.

## 10. Размер, ресурсы, репозиторий

Цель: пакет до 60 КБ на флеше и до 3 МБ ОЗУ в простое. На минимальном роутере клиента (128 МБ флеша, 256 МБ ОЗУ) это меньше 0,1% флеша и около 1% памяти; основную память занимает sing-box из podkop.

**Зависимости**

- `ucode` + `rpcd-mod-ucode` — служба, CLI и бэкенд LuCI; JSON разбирается встроенно, `jq` не нужен. Уже стоят на тестовом роутере.
- `curl` — для `PATCH` и `PUT` (встроенный `uclient-fetch` умеет только GET/POST). Обычно приходит с podkop; если нет — ставится установщиком.
- `uencrypt` (≈10 КБ) — шифрование данных хранилища и секретов.
- `ping` из busybox.
- На роутере — без Python, Node, базы данных и своих бинарников.

**Ресурсы**

- Одна служба procd с циклом раз в 45 с; между итерациями спит.
- Флеш пишется только при смене ссылки, токена или настроек; кэш и счётчики — в `/tmp`.
- Сеть в простое на роутер: 1 запрос к GitHub в минуту (обычно 304), 2 маленькие HTTPS-проверки в 45 с; к StealthSurf — только у одного роутера привязки, раз в 10 мин.

**Репозиторий кода** (публичный, чтобы установка шла одной командой; секретов в нём нет):

```
peers-ss/
  install.sh                 # режимы: новый контур / --join PSS1.…
  files/usr/bin/peers-ss     # ucode: служба + CLI (status, rotate, token, diag, uninstall)
  files/usr/share/peers-ss/  # модули: api.uc, store.uc, crypto.uc, podkop.uc, health.uc
  files/etc/init.d/peers-ss
  files/etc/config/peers-ss
  files/usr/share/rpcd/ucode/peers-ss.uc
  files/usr/share/rpcd/acl.d/luci-app-peers-ss.json
  files/usr/share/luci/menu.d/luci-app-peers-ss.json
  files/www/luci-static/resources/view/peers-ss/*.js
  bot/                       # Telegram-бот: Python, systemd unit, README по установке
  .github/workflows/release.yml  # собирает .ipk (arch all) и tar.gz в Releases
  docs/SPEC.md               # этот документ
  AGENTS.md                  # для OpenCode
  CLAUDE.md                  # для Claude Code (ссылка на AGENTS.md)
```

Установщик скачивает файлы из последнего GitHub Release, а не из ветки `main`, чтобы роутеры не получали недоделанный код. Хранилище `peers-ss-state` — отдельный приватный репозиторий, код туда не кладётся.

## 11. Этапы для Claude Code / OpenCode

Агент идёт этапами и не начинает следующий, пока проверка текущего не прошла на тестовом роутере. Этот документ кладётся в репозиторий как `docs/SPEC.md` (экспорт в Markdown), а в `AGENTS.md` и `CLAUDE.md` — правила ниже и ссылка на него.

0. **Подготовка (делаете вы).** Купить конфиг StealthSurf `Test-conf`; на тестовом роутере установить podkop 0.7.24 и убрать ссылку Tailscale из `remote_domain_lists` секции `KCA`.
1. **Разведка, ничего не меняя.** По SSH: версия прошивки и podkop, `/etc/config/podkop`, что делает «Применить» в LuCI podkop, команды диагностики podkop, есть ли Clash API и `mixed_proxy` на `127.0.0.1`, наличие `curl`, `ucode`, `rpcd-mod-ucode`, `uencrypt`, свободное место. По API с `Test-conf`: как в `GET /locations` помечены «Умная» и «Россия». Итог — `docs/RECON.md`.
2. **Клиент API StealthSurf (только чтение).** Проверка: по токену выводится нумерованный список `vless`-конфигов, выбор по номеру сохраняется; пинг до `ping_ip` всех локаций снимается за 10 с.
3. **Хранилище и шифрование.** Чтение с ETag, запись с `sha`, шифрование `uencrypt`. Проверка: две одновременные записи из двух shell — проходит одна, вторая повторяет без потери данных; в репозитории виден только шифр.
4. **podkop: вставка, применение, диагностика, пинг.** Проверка: ссылка `Test-conf` в LuCI podkop, туннель работает, диагностика зелёная, пинг записан; повторная вставка той же ссылки ничего не пишет.
5. **Проверка, ротация, доставка.** Проверки: (а) на одном роутере «заблокировать» текущий сервер правилом nftables, отбрасывающим его IP → все роутеры привязки на новом сервере меньше чем за 5 мин, время в отчёт; (б) отключить WAN → ротации нет; (в) блокировка на двух роутерах одновременно → ровно один `PATCH`; (г) блокировка на ведомом роутере → ротирует роутер с токеном; (д) провал 3 кандидатов → режим ожидания и повтор через 10 мин.
6. **Установщик (режим А) и токен.** Новый контур, автогруппа, `openwrt-1`; установка без токена и добавление позже; замена и удаление токена.
7. **LuCI.** Все вкладки, «Состав», смена схемы с архивом; правка на одном роутере видна на другом за минуту; конфликт одновременной правки.
8. **Ссылки и `--join`.** На втором роутере или виртуальном OpenWrt x86 на Ubuntu-сервере: ссылка регистрирует `openwrt-2`, повторно не срабатывает, отзыв работает, неверный пароль контура не пускает.
9. **Telegram-бот.** На Ubuntu-сервере: регистрация клиента, привязка конфига, напоминание с тестовой датой окончания, алерты; запуск после выключения в 21:00.
10. **Релиз.** GitHub Actions собирает `.ipk` и архив; `uninstall` чистит всё; настройки переживают sysupgrade; замер размера пакета и ОЗУ службы.

**Правила для агента**

- Работать только на тестовом роутере. `PATCH` к StealthSurf — только для `Test-conf`: каждая ротация реально переносит конфиг для всех его устройств.
- Перед первым изменением — копия `/etc/config/podkop`. В podkop не трогать ничего, кроме управляемой секции и её строки прокси.
- Не печатать токены, пароль контура и ссылки `vless://` в логи, вывод команд и коммиты.
- Не перезагружать роутер и не обновлять прошивку или podkop без вопроса.
- Не выдумывать поля API и опции podkop: сверяться с [документацией StealthSurf](https://docs.stealthsurf.net/api), реальными ответами и кодом установленного podkop.

## 12. Открытые вопросы

Основные решения приняты (раздел 1). Остались мелочи с вариантом по умолчанию — агент берёт его, если не сказано иное.

- [ ] **Доступ клиентов к LuCI.** По умолчанию: у клиентов доступа нет, в LuCI заходит только администратор под root; клиент видит свой конфиг через бота.
- [ ] **После окончания конфига.** По умолчанию: одно сообщение «истёк» на следующий день, дальше тишина до продления.
- [ ] **Порог «роутер не на связи».** По умолчанию 1 час.
- [ ] **Менять ли системный hostname** вместе с именем `openwrt-N`. По умолчанию нет.
