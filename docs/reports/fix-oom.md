# v1.2.1 — служба без долгоживущего процесса (OOM на роутере 1)

## Симптом
2026-11-24 роутер 1 (192.168.200.1, 240 МБ ОЗУ, без swap) сильно тормозил: веб-интерфейс почти не открывался, лагала даже SSH-сессия.

## Причина
- `dmesg`: `Out of memory: Killed process 8348 (peers-ss) … anon-rss:61468kB`. Резидентный `ucode /usr/bin/peers-ss daemon` за двое суток вырос до 61 МБ при цели ТЗ «до 3 МБ в простое». Раньше от нехватки памяти пострадал и `tailscaled` (62 МБ).
- Один интерпретатор сутками гонял `E.tick()`: вывод curl, большие JSON, расшифровку. Память системе не возвращалась, пока ядро не убивало процесс. procd перезапускал его, и всё повторялось.
- Кроме того, демон перезапускал podkop при `podkop_down`, даже если владелец сам остановил podkop.

## Что сделано (по модели podkop: резидентен только sing-box, остальное — короткие команды)
- `/etc/init.d/peers-ss` запускает `/bin/sh /usr/share/peers-ss/loop.sh`. Цикл раз в `check_interval_s` (по умолчанию 45 с) запускает отдельный процесс `peers-ss tick`, который делает одну итерацию и завершается.
- То, что раньше жило в ОЗУ демона, переехало в `/tmp/peers-ss`:
  - часы GitHub и время последнего успешного ответа — `store/runtime.json`;
  - старт отсчёта «GitHub недоступен» — `state.json:start_mono`;
  - кэш записей роутеров — `recs.json`;
  - медленная часть снимка LuCI — `ui-slow.json`.
- `read_dir` берёт неизменившиеся файлы из дискового кэша: sha листинга совпадает с sha блоба. Новый процесс не делает лишних GET.
- Остановленный владельцем podkop больше не поднимается:
  - признак — `podkop.settings.shutdown_correctly=1`, его пишет `podkop stop`;
  - блокировки, наш перезапуск и наша аварийная остановка оставляют метку `/tmp/peers-ss/podkop-restart`. Поэтому неудачный `start` (он выходит раньше, чем записывает 0) не принимается за решение владельца;
  - любое применение ссылки (`apply_link`) откладывается, и `applied_rev` не сдвигается, так что ссылка применится после запуска podkop. Ротация и сверка с API при `podkop_down` не выполняются;
  - перезапуск упавшего podkop — не чаще раза в 10 минут.
- Остановка службы: trap в цикле гасит текущий `tick`. ucode перехватывает SIGTERM и может отложить его на время `popen`/`sleep`, поэтому через 3 с процесс добивается SIGKILL. Осиротевший tick не пишет в GitHub после `stop`/`uninstall`; `uninstall` дополнительно добивает процессы `tick`.
- Ошибки tick идут в stderr → procd → logread. `peers-ss daemon` теперь подсказывает новую команду; одна итерация — `peers-ss tick`.
- Состояние перечитывается после взятия блокировки движка: CLI `rotate` или задание rpcd могли его изменить.

## Ревью
Ревью проводил отдельный субагент с чистым контекстом. Исправлено всё найденное:
- обход защиты podkop через ротацию, `reconcile` и путь «GitHub недоступен»;
- ложный флаг после неудачного `start`;
- осиротевший tick;
- лишние запросы `read_dir`;
- потерянный stderr;
- `daemon` через `system(exec)`;
- `runtime.json` после убитого tick;
- нули в начале значения интервала;
- состояние, прочитанное до взятия блокировки.

## Проверка на роутере 1
- Один `tick`: rc=0, статус `ok`, пик RSS ≈ 2,6 МБ, после завершения — 0.
- Цикл `loop.sh`: RSS ≈ 1 МБ.
- `stop` во время tick: в 4 раундах из 4 не осталось ни одного процесса.
- Замер 10 минут (14:46–14:56, 13 итераций): пик RSS tick 2,4–2,5 МБ, цикл 1 040 КБ без роста, MemAvailable 52–60 МБ (до исправления 45 МБ, затем OOM), load 0,02–0,20, ошибок в logread нет.
- Сценарий «владелец остановил podkop» на живом podkop не прогонялся: podkop без вопроса владельцу не трогаем. Логика проверена ревью и чтением `/usr/bin/podkop` 0.7.24 (`start`/`stop` → `shutdown_correctly`).
