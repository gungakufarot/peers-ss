# Peers-SS — итоговый отчёт

Дата: 22.11.2026. Релиз: **v1.0.2** (https://github.com/gungakufarot/peers-ss/releases/latest). Все этапы раздела 11 ТЗ пройдены;
по каждому — отчёт `docs/reports/stage-N.md` с проверками, ревью независимого субагента и исправлениями.

## Что работает
- **Служба на роутере** (ucode, procd): 4 слоя проверки каждые 45 с, порог 3 сбоя; ротация через API StealthSurf с замком в хранилище
  (сроки по `Date` GitHub, продление перед каждым PATCH), выбор локации по минимальному пингу (кроме «Умной» `RB` и России `RU`),
  серверы по пингу, чёрный список 24 ч, история 10, правило «не чаще раза в 10 мин», режим ожидания с повтором раз в 10 мин (1 кандидат);
  доставка ссылки остальным роутерам через `rotations/…` (ETag/304), применение в podkop как «Сохранить и применить», диагностика podkop,
  пинг через vless (Clash API); ведомые роутеры пишут отчёт о блокировке — ротирует роутер с токеном; защита «плохой канал»;
  режим «GitHub недоступен»; сверка с API раз в 10 мин; алерты и карточки для бота.
- **Хранилище**: приватный `peers-ss-state`, файлы `{"schema":1,"enc":"PSE1…"}` — AES-256-CBC (`uencrypt`) + HMAC-SHA256 с привязкой к пути
  и схеме, анти-откат по `rev`, CAS по `sha`, ключ — 100 000 итераций SHA-256 от пароля контура.
- **Установщик** (режимы А и Б), одноразовые ссылки `PSS1.…`, управление токеном, `uninstall`, `.ipk`, обновление поверх установки.
- **LuCI** Services → Peers-SS: 8 вкладок по ТЗ, «Состав», смена схемы с архивом, конфликт одновременной правки, назначение конфига через
  токен другого роутера, смена пароля контура (остальные роутеры переходят сами), пробная ротация, отчёт без секретов.
- **Telegram-бот** на 169.58.31.113: регистрация клиентов, привязка, напоминания в 21:00 МСК, алерты, тихий режим, админка, копия базы.

## Время ротации, размер, ОЗУ
- Время от блокировки до новой ссылки на всех роутерах: **153–182 с** (обнаружение 3×45 с + ротация ~20–40 с + доставка ≤60 с);
  без GitHub — до ~8,5 мин (остальные получают ссылку сверкой с API раз в 10 мин; ведомые ждут GitHub — как в ТЗ).
- Пакет: **`.ipk` 52 КБ**, `.tar.gz` 51 КБ; несжато 172 КБ; на флеше ubifs ≈ 200 КБ. Цель «60 КБ на флеше» **не достигнута** (см. ограничения).
- ОЗУ службы в простое: **2,3–2,9 МБ RSS** (цель ≤ 3 МБ — выполнена). Бот: пик 19,5 МБ.

## Решения и отклонения от ТЗ (подробно — в отчётах этапов)
- Протокол конфигов в API — `vless-2410`; «vless-конфиг» = ссылка `vless://`, в PATCH передаётся протокол конфига.
- `GET /configs` не отдаёт `xray_config` → флаги для PATCH выводятся из ссылки (`security`, `type`, `fp`); остальные флаги (warp, DNS,
  фильтры) API не показывает — могут сброситься при PATCH.
- PATCH с `server_ids` в той же локации может оставить прежний сервер → сравнение сервера/IP, повтор с явным `server_id`, затем другая локация.
- Проверено: PATCH сразу обновляет `GET /configs` (кэш 300 с не мешает); защита от устаревшего ответа оставлена.
- `routers/<id>.json` — пульс раз в 30 мин (а не 6 ч), иначе нельзя ловить «не на связи > 1 ч».
- Ротация по отчёту ведомого пропускает перепроверку слоёв 3–4 у ротатора (иначе сценарий (г) невыполним).
- Трафик самого роутера к API/GitHub: вместо «исключений podkop» (опция `enable_output_network_interface` в podkop 0.7.24 делает другое)
  хосты резолвятся через публичные DNS и соединение идёт на реальный IP — мимо туннеля при любых списках клиента и без зависимости от DNS sing-box.
- Токен GitHub бота: ТЗ требует «только чтение» и одновременно ежедневную копию базы в хранилище — несовместимо; токен RW, копия шифруется
  отдельным `BACKUP_KEY`. Без `BACKUP_KEY` бот работает только на чтение.
- Секцию podkop `KCA` (и ссылку Tailscale в ней) не трогали — по решению владельца; связанный с ней шум в логе podkop — известный.
- Защита PATCH «только Test-conf» — **настройка тестового режима** `peers-ss.main.test_patch_allow`, ставится только на тестовых роутерах;
  **в релизе её нет** (`files/etc/config/peers-ss` без неё, CI проверяет).

## Известные ограничения
1. Флеш: ~200 КБ на ubifs вместо 60 КБ (много мелких файлов: 12 модулей ucode + 9 JS LuCI). Уменьшается склейкой модулей.
2. Зависимости: `ucode-mod-digest` (65 КБ, SHA-256) и `uencrypt-*`; ключ AES на долю секунды виден в `/proc/*/cmdline` (у uencrypt нет иного способа).
3. Смена пароля контура не отзывает утёкший старый пароль (цепочка `rekeys`); полный отзыв — замена токена GitHub на всех роутерах.
4. Код приглашения содержит токен GitHub с правом записи; с ним возможен офлайн-подбор пароля контура — нужен длинный пароль/фраза.
5. Без GitHub ведомые роутеры не получают новую ссылку до его возвращения; остальные — до 10 мин (сверка с API).
6. Двойная смена сервера в режиме без GitHub возможна (ТЗ §5), риск снижен паузой 0–90 с.
7. r2: провайдерский путь до DNS 1.1.1.1/UDP нестабилен → диагностика podkop там красная (`dns_on_router: 0`) — настройки podkop
   владельца вне управляемой секции не менялись.
8. После sysupgrade нужно заново поставить podkop и Peers-SS (настройки сохраняются, ввод данных не нужен); podkop оставляет в
   `/etc/config/dhcp` перенаправление DNS — останавливать podkop перед прошивкой.
9. «Плохой канал» реализован, но отдельным тестом не проверялся (нет в списке проверок ТЗ).
10. LuCI проверялась на VM (пароль LuCI роутера 1 агенту неизвестен); бэкенд на r1/r2 — через ubus/CLI.
11. На сервере бота IPv6 до Telegram зависает в long polling — бот принудительно использует IPv4 (`BOT_IPV6=1` — вернуть).

## Что сделать владельцу
- Перевыпустить токены (значения в `/root/peers-ss-secrets.env` однажды попали в вывод агента в начале работы) и положить в
  `/root/peers-ss-secrets-end.env` (KEY=VALUE). На роутерах: `peers-ss token set`, `peers-ss github-token set`; на сервере — `/etc/peers-ss-bot/env`.
- Для боевых роутеров не ставить `test_patch_allow` (на тестовых r1/r2/r3 он есть: `uci delete peers-ss.main.test_patch_allow; uci commit`).
- Тестовый контур «Тест» (`c8a9d4463c410`) и VM `router3` на хосте можно удалить, когда не нужны (`peers-ss uninstall` на роутерах;
  VM: `/root/peers-ss-vm/`). Бэкапы роутеров до работ: `/root/peers-ss-backups/`.
- Для бота: при желании отдельный fine-grained токен (или убрать `BACKUP_KEY`, если нужна строго «только чтение»).
